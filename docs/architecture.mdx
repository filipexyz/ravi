## Overview

Ravi is the daemon that gives Claude a life. The daemon connects to NATS, manages agent sessions via the Claude Agent SDK, and coordinates background runners for cron jobs, heartbeat, and event triggers. Channel accounts are held by a separate process, the channel runner (`ravi channels`): WhatsApp (Baileys) and native Slack run there. Telegram and Discord go through the optional legacy Omni bridge.

## Daemon

The daemon is the main long-running process, managed by PM2. It does **not** spawn child processes — it connects to NATS and, when configured, to the legacy Omni bridge. The channel runner (`ravi channels start`) is a separate PM2 process that the daemon does not start.

**Startup sequence** (`startDaemon()` in `src/daemon.ts`):

1. **Connect to NATS** — Retries up to 30 times with 2s intervals to handle PM2 parallel startup where NATS might not be ready yet.
2. **Start ConfigStore** — Subscribes to `ravi.config.changed` for immediate cache invalidation, plus a 30-second periodic refresh as a safety net.
3. **Ensure SESSION_PROMPTS and RAVI_EVENTS streams** — Creates the JetStream work queue stream for session prompt routing and the event stream.
4. **Start RaviBot** — Initializes the Claude Agent SDK, subscribes to the session prompts consumer, and starts processing messages.
5. **Start channels** (`src/daemon-channels.ts`) — One `ChannelInboundPipeline` shared by every source: the WhatsApp source (always) and the legacy Omni bridge source (only when `OMNI_API_URL`/`OMNI_API_KEY` or `~/.omni/config.json` configure Omni). The legacy bridge is loaded with a dynamic import, so the WhatsApp path never imports `src/omni/**`.
6. **Start Gateway** — Subscribes to internal NATS events and delivers through the `ChannelSenderRouter`.
7. **Start runners** — Leader election determines which daemon runs heartbeat and cron; trigger, ephemeral, and inbox runners are per-daemon.

**Shutdown** is graceful with a 15-second timeout. The bot is stopped first (aborting SDK subprocesses), then runners release leadership, then Gateway and inbound sources stop, and finally the NATS connection is drained.

### PM2 Management

The daemon process is named `ravi` in PM2 and the channel runner `ravi-channels`. The `src/pm2.ts` module provides utilities for checking process status, reading PIDs, and running PM2 commands. CLI commands like `ravi daemon start` and `ravi daemon stop` delegate to PM2 under the hood.

## Gateway

The Gateway (`src/gateway.ts`) is the bridge between the bot's internal NATS events and the channel transports. It subscribes to internal NATS topics and delivers through the `ChannelSenderRouter`, which picks the sender for each instance (see [Channel Senders](#channel-senders)).

**Subscriptions:**

| NATS Topic | Purpose | Queue Group |
|---|---|---|
| `ravi.session.*.response` | Deliver bot responses to channels via the channel sender | `ravi-gateway` |
| `ravi.session.*.claude` | Typing indicator heartbeat (start/stop) | — |
| `ravi.outbound.deliver` | Direct channel delivery (with optional humanized delays) | `ravi-gateway` |
| `ravi.outbound.reaction` | Emoji reactions from agents | `ravi-gateway` |
| `ravi.media.send` | Media file delivery (images, videos, audio, documents) | `ravi-gateway` |
| `ravi.stickers.send` | WhatsApp sticker delivery | `ravi-gateway` |
| `ravi.config.changed` | Reload router config cache and sync REBAC relations | — |

**Queue groups** ensure that in multi-daemon deployments, only one daemon processes each delivery event. Subscriptions without a queue group are fan-out — all daemons receive the event (e.g., config changes must be applied everywhere).

**Key behaviors:**

- **Silent token** — If a bot response contains `@@SILENT@@`, the Gateway suppresses it and does not send to the channel.
- **Ghost response detection** — Responses without a `_emitId` are dropped and logged as ghost responses.
- **Sentinel humanization** — When an agent is in sentinel mode and sends via `ravi.outbound.deliver`, the Gateway auto-calculates typing delay and pause times to simulate human-like behavior.
- **Auto-reconnect** — Each subscription has automatic reconnection with a 1-second retry delay if the NATS connection drops.

## NATS

### Connection

The NATS singleton (`src/nats.ts`) supports two connection modes:

- **Explicit** (daemon) — `connectNats()` is called at startup with retry logic (30 attempts, 2s intervals). The connection monitors status changes and auto-reconnects indefinitely.
- **Lazy** (CLI) — First call to `emit()` or `subscribe()` triggers a one-shot connection. CLI commands work without explicitly connecting first.

The module exposes a `nats` convenience object with `emit()` (publish JSON), `subscribe()` (async generator with topic pattern matching), and `close()` (drain and disconnect).

**Subscribe features:**
- Variadic patterns: `subscribe("a.*", "b.*")` merges multiple subscriptions
- Queue groups: `subscribe("topic", { queue: "group-name" })` for load-balanced consumption
- Built-in dedup: filters duplicate messages from JetStream stream captures within a 250ms window

### JetStream Streams

Ravi interacts with these JetStream streams:

| Stream | Consumer | Filter | Source |
|---|---|---|---|
| `CHANNEL_INBOUND` | `ravi-whatsapp-messages` | `ravi.channel.inbound.whatsapp.message.>` | channel runner (WhatsApp messages) |
| `CHANNEL_INBOUND` | `ravi-whatsapp-reactions` | `ravi.channel.inbound.whatsapp.reaction.>` | channel runner (WhatsApp reactions) |
| `CHANNEL_INBOUND` | `ravi-whatsapp-connection` | `ravi.channel.inbound.whatsapp.connection.>` | channel runner (QR, connected, disconnected) |
| `SESSION_PROMPTS` | `ravi-prompts` | `ravi.session.*.prompt` | ravi (internal routing) |
| `RAVI_EVENTS` | — | Ravi event subjects | ravi (replay/audit) |
| `MESSAGE` | `ravi-messages` | `message.received.>` | legacy Omni bridge (Telegram/Discord) |
| `INSTANCE` | `ravi-instances` | `instance.>` | legacy Omni bridge (connection events) |
| `REACTION` | `ravi-reactions` | `reaction.received.>` | legacy Omni bridge (emoji reactions) |

`CHANNEL_INBOUND` (limits retention, file storage, 7 days) and its three durables are created by both the channel runner and the daemon, so events published before the daemon starts are kept. The WhatsApp events use the versioned envelope `WhatsAppInboundEvent` (`schemaVersion: 1`, `src/channels/whatsapp/events.ts`) and the event id as JetStream `msgID`. `MESSAGE`, `INSTANCE` and `REACTION` are created by Omni and only matter when the legacy bridge is configured. `SESSION_PROMPTS` and `RAVI_EVENTS` are created by Ravi.

**SESSION_PROMPTS** is a work queue stream (`RetentionPolicy.Workqueue`) with in-memory storage and a 60-second max age. It guarantees:
- Each prompt is delivered to exactly one daemon
- Messages are deleted after acknowledgment
- Unacknowledged messages (daemon crash) are redelivered after a 5-minute ack wait

All daemons share a single durable consumer (`ravi-prompts`). NATS automatically distributes messages across active pull subscribers in round-robin fashion.

### Internal NATS Topics (Pub/Sub)

Beyond JetStream, ravi uses plain NATS pub/sub for internal coordination:

| Topic Pattern | Purpose |
|---|---|
| `ravi.session.*.response` | Bot responses for Gateway delivery |
| `ravi.session.*.claude` | Claude SDK lifecycle events (typing) |
| `ravi.outbound.deliver` | Direct message send requests |
| `ravi.outbound.reaction` | Emoji reaction send requests |
| `ravi.media.send` | Media file send requests |
| `ravi.config.changed` | Config cache invalidation (fan-out) |
| `ravi.contacts.pending` | New pending contact notification |
| `ravi.inbound.reply` | Quote-reply from channel (approval/poll resolution) |
| `ravi.inbound.reaction` | Inbound emoji reaction (approval/poll resolution) |
| `ravi.whatsapp.qr.*` | WhatsApp QR code relay for CLI pairing |
| `ravi.whatsapp.connected.*` | WhatsApp instance connected relay |
| `ravi.bridge.qr.*` / `ravi.bridge.connected.*` | Same relays for legacy-bridge instances |
| `ravi.instances.unregistered` | Unregistered instance detection |
| `ravi.triggers.refresh` | Trigger runner hot-reload signal |

The daemon and the CLI reach the channel runner over request/reply on `_RAVI.channels.whatsapp.rpc.<instanceId>` (RPC schema version 2, methods `connection.*`, `groups.*`, `messages.*`, `presence.set`).

## Channel Inbound Pipeline

`ChannelInboundPipeline` (`src/channels/inbound/pipeline.ts`) turns inbound channel events into session prompts. Every source feeds the same pipeline:

- `WhatsAppInboundSource` (`src/channels/whatsapp/inbound-source.ts`) pulls the `ravi-whatsapp-*` durables on `CHANNEL_INBOUND`. It drops invalid envelopes and envelopes whose subject instance or kind does not match.
- `OmniLegacyInboundSource` (`src/omni/inbound-source.ts`) pulls the legacy bridge streams, only when Omni is configured. It drops every event whose channel type is in the WhatsApp family (`whatsapp-baileys`, `whatsapp`, `twilio-whatsapp`, `gupshup`), logging "Ignoring Omni event for a WhatsApp channel type; migrate with ravi instances connect".

**Consume loops** run in the background for each durable. Each loop:
1. Ensures the durable consumer exists (retries until the stream appears)
2. Pulls messages and acknowledges immediately (fire-and-forget handlers)
3. Auto-restarts with a 2-second delay on errors

### Message Processing Pipeline

When a `message.received` event arrives:

1. **Filter** — History-sync messages (`ingestMode: "history-sync"`, including offline backlog older than the channel's `offlineStaleMs`, default 10 minutes) persist chat, message and participants but never prompt an agent. Reaction-type messages are skipped.
2. **Resolve account** — Map the transport `instanceId` (UUID) to a ravi account name via ConfigStore.
3. **Route resolution** — ConfigStore resolves the message to a session key and agent (route match, then the instance agent, then the default agent).
4. **Policy enforcement** — Apply group policy (`open`/`allowlist`/`closed`) and DM policy (`open`/`pairing`/`closed`). Unallowed contacts are saved as pending.
5. **Contact scoping** — Per-agent contact visibility check (`own`/`tagged`/`all`).
6. **Slash commands** — Check for `/` prefixed commands before agent processing.
7. **Media processing** — WhatsApp media is already on disk (the runner downloads it to `~/.ravi/media/whatsapp/<instanceId>/<YYYY-MM>/`); legacy-bridge media is downloaded from the Omni HTTP API. The file is saved to the agent's `attachments/` directory and audio is transcribed via OpenAI Whisper.
8. **Format envelope** — Build the message envelope with sender info, timestamps, media, and thread context.
9. **Publish prompt** — Publish to `SESSION_PROMPTS` JetStream stream for exactly-once delivery to a daemon.

**Active mode** messages include a `source` (channel routing info) and trigger a typing indicator. **Sentinel mode** messages are observed silently with no typing and no source.

### Connection Events

- `connection.qr` — Relayed to `ravi.whatsapp.qr.{instanceId}` (WhatsApp) or `ravi.bridge.qr.{instanceId}` (legacy bridge) for CLI QR pairing
- `connection.connected` — Relayed to `ravi.whatsapp.connected.{instanceId}` or `ravi.bridge.connected.{instanceId}`

### Reaction Events

Inbound reactions are deduplicated, persisted as `chat_messages` rows with `message_type = 'reaction'`, and emitted to `ravi.inbound.reaction` for approval and poll resolution workflows.

## Channel Senders

The `ChannelSenderRouter` (`src/channels/outbound/router.ts`) is default-deny:

- a canonical WhatsApp instance (bound or not) goes to the `WhatsAppSender` (`src/channels/whatsapp/sender.ts`), which calls the channel runner over RPC. An instance without an enabled WhatsApp channel fails with `WHATSAPP_NOT_BOUND` before any RPC;
- an unmapped instance fails with `INSTANCE_NOT_FOUND` (404);
- a `twilio-whatsapp` or `gupshup` record fails with `CHANNEL_PROVIDER_UNSUPPORTED` (422);
- other instance records (Telegram/Discord) go to the legacy bridge sender, or fail with `LEGACY_BRIDGE_NOT_CONFIGURED` (503) when Omni is not configured.

The WhatsApp sender provides:

- **send()** — Text messages via `messages.sendText`. Retried on runner unavailable, `NOT_CONNECTED` and `RATE_LIMITED` (honouring `retryAfterMs`); never retried on timeout or invalid response, so a message is not sent twice.
- **sendMedia()** / **sendSticker()** — Files sent by absolute `filePath`; the runner reads them from disk (no base64).
- **sendTyping()** — Presence via `presence.set` (best-effort, never throws).
- **sendReaction()** — Emoji reactions.
- **deleteMessage()** / **editMessage()** — Delete or edit the account's own messages (`ravi.outbound.message.delete|edit`).
- **markRead()** — Read receipts (best-effort, never throws).

## RaviBot

The RaviBot (`src/bot.ts`) manages Claude Agent SDK sessions. It subscribes to the `SESSION_PROMPTS` JetStream consumer and processes prompts through streaming SDK sessions.

**Key properties:**
- **Runtime session pool** — Maximum concurrent live runtime sessions is controlled by `RAVI_RUNTIME_SESSION_POOL_MAX` (default `60`). Additional prompts are queued as pending starts until a slot is released.
- **Streaming sessions** — Each session is a persistent SDK subprocess that accepts messages via AsyncGenerator. Sessions are keyed by session name.
- **Debounce** — Messages arriving within a configurable window are combined before processing.
- **Message interrupts** — New messages can interrupt running sessions (waits for safe tool completion, then interrupts).

**Subscriptions:**
- JetStream `SESSION_PROMPTS` consumer (prompt processing)
- `ravi.inbound.reaction` (approval/poll resolution via emoji)
- `ravi.inbound.reply` (approval/poll resolution via quote-reply)
- `ravi.session.*.abort` (session abort signals)

## ConfigStore

The ConfigStore (`src/config-store.ts`) is a singleton cache for router configuration loaded from SQLite.

**Refresh strategy:**
1. **NATS subscription** — Listens on `ravi.config.changed` for immediate invalidation when any CLI command modifies config.
2. **Periodic timer** — 30-second refresh as a safety net in case NATS events are missed.

**Key methods:**
- `getConfig()` — Returns cached `RouterConfig`, loading from DB on first call.
- `resolveInstanceId(accountName)` — Maps account name to the instance UUID (`instances.instance_id`).
- `resolveAccountName(instanceId)` — Maps the instance UUID to account name.

## Leader Election

Distributed leader election (`src/leader/index.ts`) uses a NATS JetStream KV store to coordinate which daemon runs singleton tasks (heartbeat and cron runners).

**Mechanism:**
1. Daemon attempts an atomic `create` on the KV key for the role — succeeds only if the key does not exist.
2. **Winner** starts leadership renewal (every 10 seconds) and runs the associated runners.
3. **Loser** polls the KV key every 10 seconds watching for vacancy.
4. If the leader dies, its KV entry expires after the 30-second TTL. A polling daemon detects the missing key, wins `create`, and takes over.
5. On graceful shutdown, the leader explicitly deletes the key so takeover is immediate.

**Leader-elected runners:** HeartbeatRunner, CronRunner.
**Per-daemon runners** (no election needed): TriggerRunner, EphemeralRunner, InboxWatcher.

## Session Keys

Session keys (`src/router/session-key.ts`) are hierarchical strings that determine conversation isolation. The format depends on the DM scope and peer type.

### DM Session Keys

| DM Scope | Format | Example |
|---|---|---|
| `main` | `agent:{agentId}:main` | `agent:main:main` |
| `per-peer` | `agent:{agentId}:dm:{phone}` | `agent:main:dm:5511999999999` |
| `per-channel-peer` | `agent:{agentId}:{channel}:dm:{phone}` | `agent:main:whatsapp:dm:5511999999999` |
| `per-account-channel-peer` | `agent:{agentId}:{channel}:{account}:dm:{phone}` | `agent:main:whatsapp:main:dm:5511999999999` |

### Group and Channel Session Keys

Groups and channels are always fully isolated:

```
agent:{agentId}:{channel}:{account}:group:{groupId}
agent:{agentId}:{channel}:{account}:channel:{channelId}
```

Threads append `:thread:{threadId}` to the session key.

### Special Session Keys

| Type | Format | Example |
|---|---|---|
| Cron job | `agent:{agentId}:cron:{jobId}` | `agent:main:cron:abc123` |
| Event trigger | `agent:{agentId}:trigger:{triggerId}` | `agent:main:trigger:a1b2c3d4` |

```

  │                                          │
  ▼                                          ▼

  │ publish                                  │ publish

  ▼                                          ▼

  └──────────────┬───────────────────────────┘

         ChannelInboundPipeline
         ┌──────────────────────────────┐

         └──────────────┬───────────────┘

           └── legacy bridge sender ── omni REST API ──▶ Telegram/Discord
```

### Delivery (Agent to Channel)

Agents send messages by emitting to internal NATS topics. The Gateway picks up the event and delivers through the `ChannelSenderRouter`:

- **Bot responses**: `ravi.session.*.response` → Gateway → channel sender
- **Direct sends**: `ravi.outbound.deliver` → Gateway → channel sender (with optional typing delay and pause)
- **Reactions**: `ravi.outbound.reaction` → Gateway → channel sender
- **Media**: `ravi.media.send` → Gateway → channel sender
