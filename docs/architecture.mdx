This page gives you a working mental model of a Ravi install: which processes run, who starts each one, how a Slack or WhatsApp message reaches an agent and how the reply gets back, and where state lives. Use it when something does not answer and you need to know where to look.

## The picture

```
        Slack                                    WhatsApp
          ^                                          ^
          | Socket Mode, Web API                     |
          v                                          v
  +----------------+                       +------------------+
  | ravi-channels  |                       | omni-api :8882   |
  | Slack runner   |                       | Omni bridge      |
  +----------------+                       +------------------+
     |          ^                             |             ^
     | prompts  | outbound jobs               | inbound     | replies
     v          |                             v             | (HTTP)
  +----------------------------------------------------+    |
  | NATS JetStream :4222  (omni-nats or nats-server)   |    |
  +----------------------------------------------------+    |
     |          ^                                           |
     | prompts  | outbound jobs, events                     |
     v          |                                           |
  +----------------------------------------------------+    |
  | ravi (the daemon)                                  |----+
  | sessions, routing, providers, cron, triggers,      |
  | heartbeat, HTTP gateway, Console poller            |<----> Ravi Console
  +----------------------------------------------------+
     |
     v
  ~/.ravi/*.db, ~/ravi/<agent>/
```

## Processes

Ravi runs as PM2 processes. Each one is started by a different command.

| Process | Role | Started by |
|---|---|---|
| `ravi` | The daemon. Runs agent sessions, routing, providers, cron, heartbeat, triggers, the WhatsApp side of channels, and the optional HTTP gateway. | `ravi daemon start` (also run by `ravi setup`) |
| `ravi-channels` | The native channel runner. Holds the Slack Socket Mode connection and delivers Slack replies. | `ravi channels start` |
| `omni-api` | The Omni bridge for WhatsApp, on port 8882. | `omni install`, then `omni start` |
| `omni-nats` | NATS with JetStream on port 4222. | `omni install`, then `omni start` |

`ravi daemon start` starts only `ravi`. If you use Slack, you also run `ravi channels start` once. If you skip Omni because you only use Slack, you run your own `nats-server` under PM2 instead of `omni-nats` (see [Install](/start/install)).

Restarting the daemon does not restart the runner, and the other way around. `ravi update` restarts both.

## NATS JetStream: the bus

Every Ravi process talks through one NATS server with JetStream, at `NATS_URL` (default `nats://127.0.0.1:4222`). Ravi does not ship a NATS server. It uses the one Omni installs, or one you run yourself.

Ravi creates these streams itself: the daemon creates `SESSION_PROMPTS` and `RAVI_EVENTS` at start, and the channel runner creates `CHANNEL_OUTBOUND`.

| Stream | Carries | Notes |
|---|---|---|
| `SESSION_PROMPTS` | Prompts for sessions (`ravi.session.<name>.prompt`) | Work queue. A prompt nobody picks up within 60 seconds is dropped. |
| `CHANNEL_OUTBOUND` | Outbound jobs for native channels (Slack) | Kept 7 days, up to 256 MB. |
| `RAVI_EVENTS` | Session, audit, inbound, contact, Console and other events | Kept 7 days, up to 512 MB. Read it with `ravi events replay`. |

Omni owns the `MESSAGE`, `INSTANCE` and `REACTION` streams, which the daemon reads. See [Events](/reference/nats-events) for every topic.

## How a message flows

<Tabs>
  <Tab title="Slack (native)">
    **Inbound.** Slack sends the event to `ravi-channels` over Socket Mode. The runner resolves the channel account, applies the instance policies and routes, picks the agent and session, saves any attachment into the agent's working directory, and publishes a prompt to `ravi.session.<name>.prompt`. The daemon picks it up from `SESSION_PROMPTS` and runs the turn.

    **Outbound.** When the agent replies, the daemon's delivery layer sees that the target channel is Slack and writes an outbound job to `CHANNEL_OUTBOUND`. The runner consumes the job and posts it with the Slack Web API, in the thread the routing policy chose. While the turn runs, the runner shows a "working" status in the thread.

    Slack tokens are read by the runner from the credential broker. See [Slack](/channels/slack).
  </Tab>
  <Tab title="WhatsApp (Omni)">
    **Inbound.** `omni-api` receives the WhatsApp message and publishes it to Omni's `MESSAGE` stream as `message.received.<channelType>.<instanceId>`. The daemon reads that stream, resolves the instance, applies policies and routes, downloads media into the agent's working directory, and publishes a prompt to `ravi.session.<name>.prompt`. Messages that Omni marks as history sync, and messages older than the daemon's start, are stored but do not start a turn.

    **Outbound.** The daemon's delivery layer sends the reply to `omni-api` over HTTP, using `OMNI_API_URL` and `OMNI_API_KEY` or `~/.omni/config.json`.

    See [WhatsApp](/channels/whatsapp).
  </Tab>
</Tabs>

Routing is the same for both: an instance maps a channel account to an agent, routes override that per chat pattern, and the DM scope decides which messages share a session. See [Routing](/guides/routing).

## Sessions and the runtime

A session is one conversation thread with an agent, with its own history and provider state. Its key encodes where it came from, for example `agent:main:dm:<peer>` or `agent:main:slack:<account>:group:<id>`. See [Sessions](/guides/sessions).

When a prompt arrives, the daemon runs the turn with the session's **provider**, in the agent's working directory (`~/ravi/<agent>`), which holds the agent's `AGENTS.md`:

| Provider | Runs |
|---|---|
| `claude` | The Claude Agent SDK. Recommended. |
| `codex` | The Codex CLI. The built-in default. |
| `pi` | The `pi` CLI. |
| `grok` | The `grok` CLI. |

A session uses its own override if it has one (`ravi sessions set-provider`), otherwise the provider it last used, then the agent's preset or `provider`, then the `runtime.defaultProvider` setting, then `codex`; `ravi agents set` moves sessions that have no override to the agent's new provider. Set your agent explicitly:

```bash
ravi agents set main provider claude
```

Messages that arrive while a turn runs are queued and delivered in order. Agents use the `ravi` CLI as their tools, checked against their permissions (see [Permissions](/guides/permissions)). Provider CLIs that run in a sandbox reach `ravi` through a local socket, `~/.ravi/cli-gateway.sock`.

## Background runners

Inside the daemon, runners handle work that is not a reply to a message: cron jobs, heartbeats, event triggers, hooks, background jobs, task checkpoints and the Console inbox poller.

If you run more than one daemon against the same NATS server, they elect a leader through a NATS key-value lease (30 seconds, renewed every 10). Only the leader runs cron, heartbeat and the other scheduled runners, so a job never fires twice. Every daemon runs triggers, hooks and the Console poller.

## Storage

| Path | Holds |
|---|---|
| `~/.ravi/ravi.db` | Agents, instances, routes, channels, sessions, settings, cron jobs, triggers, chats. |
| `~/.ravi/chat.db` | Contacts, platform identities, contact policies and messages. |
| `~/.ravi/credentials.db` | Credential broker metadata. Secrets stay in the Keychain or Vault. |
| `~/.ravi/.env` | Process environment for the daemon and the CLI. |
| `~/ravi/<agent>/` | Each agent's working directory, `AGENTS.md`, and received attachments. |
| `~/.omni/` | Omni's config, data and logs. |

All of it is local SQLite and files. The full list is in [Configuration](/reference/configuration#files-on-disk).

## HTTP gateway and SDK

Set `RAVI_HTTP_PORT` and the daemon serves an HTTP API on `127.0.0.1` (change it with `RAVI_HTTP_HOST`). Under `/api/v1/` it exposes the CLI's commands (a few long-running ones stay CLI-only), authorized with `Authorization: Bearer rctx_...` runtime context keys. The same server receives webhooks. Binding a non-loopback address requires `RAVI_GATEWAY_NETWORK_AUTHORIZED=1`. The gateway builds its routes from the CLI's command registry, and the TypeScript, Dart and Swift SDKs and the OpenAPI spec are generated from it; the pre-push hook and CI fail if they drift. See [SDKs and HTTP gateway](/guides/sdk).

## The Ravi Console

The Console (`https://console.ravi.bot`) is optional. `ravi login` links this install to your Console organization and stores the login in `~/.ravi/cloud-auth/`. After that:

- **Inbox.** The daemon polls the Console agent inbox every 15 seconds and publishes each item locally on `ravi.console.inbox.item`, where triggers can react to it. Without a login the poller stays paused.
- **Pages.** `ravi pages ship` publishes HTML to your project host, `<org>-<project>.ravi.page`. See [Pages](/console/pages).
- **Bases.** `ravi bases` manages typed tables in a Console project. `ravi bases subscribe <base>` sends row changes to the inbox, so they arrive as events. See [Bases](/console/bases).

See [Log in to the Console](/console/login).
