By the end of this page you will be able to add a person as a contact, link their Slack and WhatsApp identities to one record, find and tag contacts, approve or block someone, and decide whether Ravi creates contacts on its own.

## What a contact is

A contact is a person or an organization. Groups, channels, threads and sessions are not contacts; they are chats (see [Instances and routing](/guides/routing)).

Each contact has:

- an **id**, 12 hex characters, for example `37d471eab289`;
- one or more **identities**: a phone number, a WhatsApp LID, a Slack member id (`U...`), a Telegram id, an email;
- a **status**: `allowed`, `pending`, `blocked` or `discovered`;
- **tags**, and properties such as name, email, notes and opt-out.

Contacts matter because a message is tied to a person only when the sender's identity is linked to a contact. A sender without a contact gets no tools in that turn, and a contact can hold permission tags and grants. See [Permissions](/guides/permissions).

## Add a contact

<Tabs>
  <Tab title="Slack">
    ```bash
    ravi contacts add U0123ABCD "Ana Souza" --channel slack --instance slack-main
    ```

    `--instance` is the name of your Slack instance. Without `--channel slack`, Ravi refuses a Slack id and tells you to add the flags.
  </Tab>
  <Tab title="WhatsApp or phone">
    ```bash
    ravi contacts add 5511999999999 "Ana Souza"
    ```

    Use the full international number, digits only.
  </Tab>
</Tabs>

The command prints the new id:

```text
✓ Contact added: 37d471eab289 (Ana Souza) — slack:U0123ABCD
```

`add` creates the contact with status `allowed`. Other options: `--kind person|org`, `--agent <ids>` (see [Restricting to agents](#restricting-to-agents)), and `--channel telegram|email|whatsapp|phone`. Telegram ids also need `--instance`.

<Warning>
`contacts add --instance` does not check that the instance exists. A typo leaves the identity attached to an instance that never receives messages, and the person is not recognized. Check the name with `ravi instances list` first.
</Warning>

## Link more identities

Link every identity a person uses to the same contact, so their tags and grants follow them across channels:

```bash
# Created from Slack: add their WhatsApp number
ravi contacts link 37d471eab289 --channel whatsapp --id 5511999999999

# Created from a phone number: add their Slack member id
ravi contacts link <contact-id> --channel slack --id U0123ABCD --instance slack-main

ravi contacts info 37d471eab289
```

`--channel whatsapp` with a number stores a phone identity; a WhatsApp LID is passed as `lid:<digits>`. `contacts info` lists every identity, and `contacts check` is the same command.

To detach an identity, or to fold a duplicate record into another:

```bash
ravi contacts unlink U0123ABCD --channel slack
ravi contacts duplicates
ravi contacts merge <source-id> <target-id>            # dry-run, exit 3
ravi contacts merge <source-id> <target-id> --execute  # moves identities, deletes the source
```

## Find and inspect

```bash
ravi contacts list
ravi contacts list --status pending
ravi contacts list --fields id,name,status --json
ravi contacts find "Ana"
ravi contacts find vip --tag
ravi contacts info <contact>
ravi contacts timeline <contact>
```

Every command that takes `<contact>` accepts the contact id or any of its identities. `list` ends with a count by status, for example `Total: 2 (2 returned, limit 50, offset 0; 2 allowed, 0 pending, 0 blocked, 0 discovered)`.

## Tags, notes and properties

```bash
ravi contacts tag <contact> vip
ravi contacts untag <contact> vip
ravi contacts set <contact> tags '["lead","vip"]'        # replaces all tags
ravi contacts set <contact> email ana@example.com
ravi contacts set <contact> notes '{"company":"Acme"}'
ravi contacts note <contact> "Asked for a callback on Monday"
```

`set` accepts `name`, `email`, `tags`, `notes`, `opt-out`, `source`, `allowed-agents` and `mode`. Use `-` to clear `name`, `email`, `source` or `allowed-agents`. `note` appends an entry to the contact's timeline.

Tags are labels. The only tags that grant authority are `permission-admin`, `permission-owner` and `permission-superadmin`, which give `admin:system:*` while the contact is `allowed`. They apply immediately, with no dry-run, so tag carefully. See [Make yourself the owner](/start/owner).

## Status

| Status | How a contact gets it | What it changes today |
|---|---|---|
| `allowed` | `add`, `approve`, `allow` | Passes WhatsApp DMs under `pairing`. Required for admin tags to count and for approving requests. |
| `pending` | Contact intake in `pending` mode, or `contacts backfill` | Listed by `ravi contacts pending`. Treated as not allowed. |
| `discovered` | Contact intake in `discovered` mode, or `contacts backfill` | Known but not waiting for review. Treated as not allowed. |
| `blocked` | `block` | Loses every permission tag and chat grant. Held for review like any non-allowed sender in WhatsApp DMs under `pairing`. |

All status changes apply immediately:

```bash
ravi contacts approve <contact>    # status allowed
ravi contacts allow <contact>      # status allowed
ravi contacts block <contact>      # status blocked
```

These commands refuse group and chat ids. Approve a chat with `ravi instances pending approve` or add a route instead.

<Warning>
Blocking does not keep someone out on its own. Under an `open` policy a blocked contact's messages still start turns, and native Slack never looks at contact status. In a chat that is not governed, a blocked contact who reaches the agent still gets the agent's full ceiling. To keep people out, use entry policies and explicit routes ([Instances and routing](/guides/routing)); on Slack, keep DMs on `pairing` and route only the people you trust.
</Warning>

## Pending approvals

People land in review in two ways: contact intake creates them as `pending`, or a `pairing` policy holds their DM. Groups held by an `allowlist` policy show up in the same list as pending chats; approve those as described in [Instances and routing](/guides/routing).

```bash
ravi contacts pending                               # everything waiting, all instances
ravi instances pending list wa-main                 # one instance
ravi instances pending approve wa-main 5511999999999
ravi instances pending reject wa-main 5511999999999 --execute
ravi contacts approve <contact>                     # a contact created by intake
```

`instances pending approve` marks the sender `allowed`, which releases WhatsApp DMs under `pairing`. `reject` is a dry-run (exit 3) until you pass `--execute`.

<Note>
On native Slack, approving a held DM sender does not release their DMs: the `pairing` gate there needs an explicit route. See [Connect Slack](/channels/slack).
</Note>

## Contact intake

By default Ravi does not create contacts from incoming messages: an instance's `contactIntakeMode` is `off`. Turn it on per instance:

```bash
ravi instances set wa-main contactIntakeMode discovered     # or pending, or off
ravi instances set wa-main defaultContactTags new-contact   # tags for contacts intake creates
```

With intake on, a new sender becomes a contact with status `discovered` or `pending` and their identity is linked. On WhatsApp this covers DMs, and group senders whose phone number the provider resolves. Default tags apply only when intake creates the contact.

<Warning>
Intake makes strangers resolvable. In a chat that is not governed, any sender who resolves to a contact gets the agent's full ceiling, whatever their status. With intake `off`, unknown senders get no tools. Turn intake on only where entry policies already keep strangers out, or where the agent's ceiling is narrow.
</Warning>

To create contacts for DMs that arrived before intake was on, run a backfill. It previews by default:

```bash
ravi contacts backfill --instance wa-main --mode discovered
ravi contacts backfill --instance wa-main --mode discovered --apply
```

Backfill never creates contacts for groups, and never changes the status of `allowed` or `blocked` contacts.

## Restricting to agents

`--agent` on `add` or `approve`, or `set allowed-agents`, stores a list of agents for the contact:

```bash
ravi contacts approve <contact> --agent sales,support
ravi contacts set <contact> allowed-agents '["sales"]'
ravi contacts set <contact> allowed-agents -              # clear
```

Only DMs that arrive through Omni, such as WhatsApp, check this list: a message from an `allowed` contact routed to an agent that is not on the list is dropped. Native Slack ignores it. To choose which agent answers whom, use routes ([Instances and routing](/guides/routing)).

## Reply mode

`approve <contact> mention` and `set <contact> mode mention` store a reply mode, shown as `Mode` in `contacts info`. No channel enforces it today: the agent does not filter replies by mention. In groups, whether the agent speaks up is left to its instructions, and on Slack every human message in a routed channel starts a turn.

## Removing a contact

```bash
ravi contacts remove <contact>             # dry-run, exit 3
ravi contacts remove <contact> --execute
```
