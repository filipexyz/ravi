## Prerequisites

Install the NATS CLI:

```bash
brew install nats-io/nats-tools/nats
```

Connection shortcut:

```bash
alias nats-local='nats --server nats://127.0.0.1:4222'
```

## Streams Overview

```bash
nats stream ls --server nats://127.0.0.1:4222
```

Ravi streams: `CHANNEL_INBOUND` (WhatsApp inbound from the `ravi channels`
runner), `SESSION_PROMPTS`, `RAVI_EVENTS`. On hosts that still use the legacy
Omni bridge for Telegram/Discord you also see `MESSAGE`, `INSTANCE` and
`REACTION`.

<Warning>
On hosts upgraded from Omni, the PM2 process `omni-nats` is Ravi's NATS. Inspect
it freely, but never run `omni stop|start|restart|install` or
`pm2 stop|delete|restart omni-nats`. `ravi daemon status --json` shows the owner
in `infrastructure.nats.processName`.
</Warning>

## Inspect a Stream

```bash
nats stream info CHANNEL_INBOUND --server nats://127.0.0.1:4222
```

Shows subjects, retention policy, message count, consumer count, and first/last sequence. `CHANNEL_INBOUND` keeps events for 7 days (limits retention, file storage).

## Read Messages

### Last message on a subject

```bash
nats stream get CHANNEL_INBOUND --server nats://127.0.0.1:4222 \
  --last-for "ravi.channel.inbound.whatsapp.message.>"
```

### Specific sequence number

```bash
nats stream get CHANNEL_INBOUND --server nats://127.0.0.1:4222 --seq 5
```

### Pretty-print the envelope

WhatsApp events use the `WhatsAppInboundEvent` envelope (`schemaVersion`, `id`,
`instanceId`, `timestamp`, `type`, `ingestMode`, `payload`):

```bash
nats stream get CHANNEL_INBOUND --server nats://127.0.0.1:4222 --seq 5 | python3 -c "
import sys, json
raw = sys.stdin.read()
start = raw.find('{')
if start >= 0:
    d = json.loads(raw[start:])
    print('TYPE:', d.get('type'), 'INGEST:', d.get('ingestMode'))
    print('PAYLOAD:', json.dumps(d.get('payload', {}), indent=2))
"
```

Legacy-bridge events (`MESSAGE` stream) keep Omni's shape, with `metadata` and
`payload` keys.

## Consumer Status

### All consumers with positions

```bash
nats consumer report CHANNEL_INBOUND --server nats://127.0.0.1:4222
```

The "ack floor" shows the last processed sequence number.

### Ravi consumers

| Stream | Consumer |
|---|---|
| `CHANNEL_INBOUND` | `ravi-whatsapp-messages`, `ravi-whatsapp-reactions`, `ravi-whatsapp-connection` |
| `SESSION_PROMPTS` | `ravi-prompts` |
| `MESSAGE` / `INSTANCE` / `REACTION` (legacy bridge) | `ravi-messages`, `ravi-instances`, `ravi-reactions` |

The `ravi-whatsapp-*` durables are created by both the runner and the daemon, so
events published while the daemon is down wait in the stream.

## Live Subscribe

Watch events in real time (plain NATS pub/sub, not JetStream):

```bash
# All WhatsApp inbound events
nats sub "ravi.channel.inbound.whatsapp.>" --server nats://127.0.0.1:4222

# One WhatsApp instance's messages
nats sub "ravi.channel.inbound.whatsapp.message.<instanceId>" --server nats://127.0.0.1:4222

# WhatsApp connection events (qr, connected, disconnected)
nats sub "ravi.channel.inbound.whatsapp.connection.>" --server nats://127.0.0.1:4222

# Pairing relays the CLI waits on
nats sub "ravi.whatsapp.>" --server nats://127.0.0.1:4222

# Legacy bridge (Telegram/Discord)
nats sub "message.received.>" --server nats://127.0.0.1:4222

# All ravi internal events
nats sub "ravi.>" --server nats://127.0.0.1:4222

# Session responses
nats sub "ravi.session.*.response" --server nats://127.0.0.1:4222

# Tool executions
nats sub "ravi.session.*.tool" --server nats://127.0.0.1:4222
```

## Replay Messages

### Create a temporary consumer

Subscribe and receive all messages from a specific sequence:

```bash
nats consumer sub CHANNEL_INBOUND \
  --server nats://127.0.0.1:4222 \
  --filter "ravi.channel.inbound.whatsapp.message.>" \
  --deliver-start-sequence 20 \
  --ack
```

Or from the beginning:

```bash
nats consumer sub CHANNEL_INBOUND \
  --server nats://127.0.0.1:4222 \
  --filter "ravi.channel.inbound.whatsapp.message.>" \
  --deliver-all \
  --ack
```

### Force reprocessing

Delete the ravi consumer and restart the daemon. Ravi recreates consumers with `DeliverPolicy.New` on startup:

```bash
nats consumer rm CHANNEL_INBOUND ravi-whatsapp-messages --server nats://127.0.0.1:4222
ravi daemon restart -m "recreate NATS consumers"
```

This only reprocesses new messages arriving after restart. For the legacy
bridge, use `MESSAGE` and `ravi-messages` instead.

## Check IngestMode

Live messages have `ingestMode: "realtime"`. History-sync messages, including
offline backlog older than the channel's `offlineStaleMs` (default 10 minutes),
have `ingestMode: "history-sync"`: Ravi stores them but never prompts an agent.

```bash
nats stream get CHANNEL_INBOUND --server nats://127.0.0.1:4222 \
  --last-for "ravi.channel.inbound.whatsapp.message.>" | \
  python3 -c "import sys,json; raw=sys.stdin.read(); d=json.loads(raw[raw.find('{'):]); print(d.get('ingestMode','NOT SET'))"
```

## Using `ravi events stream`

Ravi has a built-in event streaming command that wraps NATS subscriptions with formatting:

```bash
# Stream all events
ravi events stream

# Filter by pattern
ravi events stream -f "ravi.session.*"

# Hide noisy events
ravi events stream --no-claude --no-heartbeat

# Only show specific types
ravi events stream --only tool
ravi events stream --only prompt
ravi events stream --only audit
```

## Using `ravi events replay`

Use replay for persisted JetStream history. It reads stored stream messages, applies filters, then prints a chronological slice:

```bash
# Last 15 minutes across all non-KV streams
ravi events replay

# WhatsApp inbound messages in a fixed window
ravi events replay \
  --stream CHANNEL_INBOUND \
  --subject "ravi.channel.inbound.whatsapp.message.>" \
  --since 2026-04-19T11:35:00Z \
  --until 2026-04-19T11:45:00Z

# Find one chat/session by substring and show raw payload
ravi events replay \
  --stream CHANNEL_INBOUND \
  --subject "ravi.channel.inbound.whatsapp.message.>" \
  --chat "63295117615153@lid" \
  --contains "melhor plano" \
  --raw

# Reconstruct a session using session name/key plus its channel chat id
ravi events replay \
  --stream RAVI_EVENTS,CHANNEL_INBOUND \
  --session main-dm-615153 \
  --since 2h \
  --raw

# JSON path filters
ravi events replay \
  --stream CHANNEL_INBOUND \
  --where "payload.chatId=63295117615153@lid;payload.content.type=text"
```

Useful flags:

- `--stream CHANNEL_INBOUND,RAVI_EVENTS` (or `MESSAGE,REACTION,SYSTEM` for the legacy bridge)
- `--subject "ravi.channel.inbound.whatsapp.>"`
- `--since 15m`, `--since 2026-04-19T11:35:00Z`, or epoch milliseconds
- `--until 5m`
- `--contains "text"`
- `--where "path=value;path~=text;path!=value"`
- `--session`, `--chat`, `--agent`
- `--json` or `--raw`

`--session` attempts to resolve a Ravi session locally. When found, it matches the session name, session key, and channel chat id, so a replay can include both internal session events from `RAVI_EVENTS` and channel events from `CHANNEL_INBOUND` (or `MESSAGE`/`REACTION`/`SYSTEM` on the legacy bridge).

For complete session reconstruction, include `RAVI_EVENTS`. The channel stream alone only captures channel events; it does not capture internal runtime events such as consumed prompts, turn interrupts, tool activity, responses, delivery, or abort requests.

Delivery events use `status: "delivered" | "failed" | "dropped"` so replay can distinguish a sent response from a silent/drop/missing-target/send-error case.

## Common Debugging Scenarios

### Messages not arriving

1. Check the runner: `ravi channels status` and `ravi instances status <name> --json`
2. Check if the runner is publishing: `nats sub "ravi.channel.inbound.whatsapp.>" --server nats://127.0.0.1:4222`
3. Check consumer position: `nats consumer report CHANNEL_INBOUND --server nats://127.0.0.1:4222`
4. Check ingestMode: history-sync messages are stored but never prompt
5. Check daemon logs: `ravi daemon logs -f`. "Ignoring Omni event for a WhatsApp channel type" means the account is still connected in Omni; migrate it with `ravi instances connect <name>`

For Telegram/Discord on the legacy bridge, use `message.received.>` and the `MESSAGE` stream.

### Bot not responding

1. Check if prompts are being published: `nats sub "ravi.session.*.prompt" --server nats://127.0.0.1:4222`
2. Check SESSION_PROMPTS consumer: `nats consumer report SESSION_PROMPTS --server nats://127.0.0.1:4222`
3. Check if responses are being emitted: `nats sub "ravi.session.*.response" --server nats://127.0.0.1:4222`
4. Check Gateway delivery: `ravi daemon logs -f | grep gateway`

### Trigger not firing

1. Check if events match the topic: `nats sub "<trigger-topic>" --server nats://127.0.0.1:4222`
2. Check cooldown: trigger may be in cooldown window
3. Check blocked topics: `.prompt`, `.response`, `.claude` topics are blocked
4. Test manually: `ravi triggers test <id> --execute`
