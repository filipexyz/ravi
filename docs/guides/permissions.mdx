By the end of this page you will know what an agent is allowed to do, who can drive it from a chat, how to give one person more power in one group, how approvals work, and how to find out why something was denied.

<Note>
This page describes `ravi.bot@next`. In `@latest` (3.260927.5) there is no `explicit-only` profile, no governed chats (`--chat`, `--chat-tag`, `--force`), and no `ravi permissions deny` or `list`.
</Note>

## How it fits together

- Every permission is a **capability** string.
- Each agent has a **ceiling**: a runtime profile plus an optional list of explicit capabilities.
- Each turn gets its own authority, computed from the ceiling, who sent the message and which chat it came from.
- When a turn lacks a capability, Ravi can ask a trusted person in the chat to **approve** it for that turn.
- Some shell commands are **always blocked**, whatever the profile.
- Every denial is published on `ravi.audit.denied`.

If you only want the owner setup (agent at `full-access`, yourself as owner contact), follow [Make yourself the owner](/start/owner). This page explains what those steps do.

## Capabilities

A capability has three parts:

```text
<permission>:<objectType>:<objectId>
```

| Capability | What it allows |
|---|---|
| `use:tool:Bash` | The Bash tool |
| `execute:executable:git` | Running `git` from Bash |
| `read:contacts:list` | `ravi contacts list` |
| `mutate:contacts:*` | Every write command of `ravi contacts` |
| `execute:group:contacts` | Every `ravi contacts` command (older group form) |
| `access:session:dev-*` | Reading and messaging sessions whose name starts with `dev-` |
| `admin:system:*` | Everything. Matches every check. |

- The only wildcard is a trailing `*` on the object id: `dev-*`, `*`.
- A CLI command accepts its semantic form (`<read|mutate>:<resource>:<action>`, the action may be `*`) or the older `execute:group:<group>` form. Prefer the semantic form.
- Subcommand groups are their own objects: `ravi bases rows add` needs `mutate:bases.rows:add` or `execute:group:bases_rows`. `execute:group:bases` does not cover it.

## Agent ceilings

Set the ceiling with `ravi agents permissions`. Run it without a profile to see the current one:

```bash
ravi agents permissions main
```

| Profile | What the agent holds | Use it for |
|---|---|---|
| `bootstrap` | The birth floor (below) plus any explicit capabilities. New agents start here. | Personal agents you watch |
| `chat-only` | Nothing. Conversation only: no tools, no shell, no CLI groups, no approvals. | Reception agents |
| `explicit-only` | Exactly the `--capabilities` you list, with no birth floor | Agents that talk to people you do not fully trust |
| `full-access` | `admin:system:*`, `execute:executable:*`, `use:tool:*`, `use:toolgroup:*`, `use:skill:*` | Your own agent, when you accept the risk |
| `none` (also `clear`, `off`) | Removes the profile and the explicit list: back to `bootstrap`. Not zero authority. | Undoing a change |

```bash
ravi agents permissions main full-access                 # dry-run, exit 3, prints the plan
ravi agents permissions main full-access --execute
ravi agents permissions support chat-only                # applies immediately
ravi agents permissions public explicit-only --capabilities use:tool:Bash,read:contacts:list --execute
ravi agents permissions main bootstrap --capabilities execute:executable:curl,view:agent:* --execute
```

**Dry-run rule.** The command writes immediately when the change keeps or reduces authority. It stops with a dry-run (exit 3, nothing written) only when the change expands authority: moving to `full-access`, adding a capability the agent did not have, or leaving `chat-only` or `explicit-only` (including `none` from those). Re-run with `--execute`.

**`--capabilities` replaces the list.** Repeat the capabilities the agent already has. The seeded `main` agent starts with one explicit capability, `view:agent:*`. `--clear-capabilities` drops the list and keeps the profile.

**When changes apply.** From the agent's next turn. Ravi revokes the agent's live permission contexts when you change the ceiling, and the Bash check of a running turn reads the new ceiling at its next command. You do not need to restart the daemon or reset sessions.

See what an agent holds right now:

```bash
ravi permissions materialize --subject-type agent --subject-id main
```

### The bootstrap floor

A `bootstrap` agent holds:

- every tool the provider offers (`use:tool:*`, `use:toolgroup:*`), including file read and write tools;
- the CLI groups `sessions`, `tasks`, `specs`, `skills`, `self` and `doctor`;
- the executables `bun`, `cat`, `date`, `find`, `git`, `head`, `ls`, `nl`, `pwd`, `ravi`, `rg`, `sed`, `sort`, `tail`, `uniq`, `wc` and `xargs`;
- `read_own_contacts:system:*`.

<Warning>
The bootstrap floor is a convenience floor, not a sandbox. `bun -e` runs any code, and `find -exec` and `xargs` run other programs; the Bash check only sees `bun`, `find` and `xargs`. File tools can read and write anything the Ravi process can. For agents that talk to untrusted people, use `chat-only` or `explicit-only`.
</Warning>

## What a turn may do

The turn's authority depends on who sent the message:

| Sender | Authority of the turn |
|---|---|
| You, from the terminal (`ravi sessions send`, `ravi tui`) | The agent's ceiling |
| Cron jobs, triggers and other automations | The agent's ceiling |
| A sender who resolves to a contact, in a chat that is not governed | The agent's ceiling, whatever the contact's status (`pending`, `discovered`, even `blocked`) |
| A sender who resolves to a contact, in a governed chat | The ceiling intersected with that contact's grants for the chat. Blocked or opted-out contacts get nothing. |
| A sender with no contact | Nothing: no tools, no commands. The agent can still reply in text. |

<Warning>
With a `full-access` agent, anyone who reaches it and resolves to a contact can drive it with admin rights, unless the chat is governed. Contact tags do not restrict anyone. Keep strangers out with entry policies (`pairing` DMs, `allowlist` groups, explicit routes; see [Instances and routing](/guides/routing)), and govern group chats that include other people.
</Warning>

## Admin tags on contacts

Three contact tags grant `admin:system:*`: `permission-admin`, `permission-owner` and `permission-superadmin`. They count only while the contact's status is `allowed` and the contact has not opted out.

```bash
ravi contacts tag <contact-id> permission-owner     # applies immediately, no dry-run
ravi permissions materialize --subject-type contact --subject-id <contact-id>
```

The second command prints `admin system:* (contact-policy:contact:<id>:admin-tag)`.

The tag does two things:

1. It makes the contact an **approver** on every channel where its identity is linked.
2. It gives the contact admin inside **governed chats**.

It does not raise the agent's ceiling, and it does not limit anyone else.

## Governed chats

A chat becomes governed as soon as any contact holds a grant scoped to it. In a governed chat, each sender gets the agent's ceiling intersected with their own grants; members without a grant (and without an admin tag) get no tools. Threads inherit their chat.

<Steps>
  <Step title="Find the chat id">
    The chat must already exist in Ravi's chat ledger, so send one message there first.

    ```bash
    ravi chats list --type group --json
    ```

    `--chat` accepts the canonical chat id, or the platform id (for example a Slack `C...` id) when it matches only one chat. Inside an agent turn, `--chat current` means the turn's chat.
  </Step>
  <Step title="Plan the grant">
    ```bash
    ravi permissions allow chat-admin --to contact:<owner-id> --chat <chat-id> \
      --agent main --capabilities 'admin:system:*'
    ```

    Without `--apply` this prints a plan (`permission allow plan`) and the exact apply command. Nothing is written.
  </Step>
  <Step title="Apply and check">
    ```bash
    ravi permissions allow chat-admin --to contact:<owner-id> --chat <chat-id> \
      --agent main --capabilities 'admin:system:*' --apply
    ravi permissions list --chat <chat-id>
    ```
  </Step>
</Steps>

Grant other members their own profiles the same way, with only the capabilities they need. Revoke with `deny`; when the last grant in a chat is gone, the chat is no longer governed:

```bash
ravi permissions deny chat-admin --to contact:<id> --chat <chat-id> --apply
```

<Warning>
Use a profile name other than `owner` for chat grants. The profile name becomes a tag with a `permission-` prefix, so `allow owner` targets `permission-owner`. If you created that tag with `ravi contacts tag`, it is a plain user tag and `ravi permissions allow owner ...` fails with `Command failed unexpectedly.`
</Warning>

Notes on the flags:

- `--to contact:<id>` requires a scope: `--chat`, `--chat-tag` or `--force`. Without one the command refuses (`CHAT_SCOPE_REQUIRED`).
- `--chat-tag <tag>` covers every chat carrying that tag. Tag a chat with `ravi tags attach <tag> --chat <chat-id>`.
- `--force` grants the profile in every chat by adding the profile tag to the contact. Like the admin tags, it counts only while the contact is `allowed`. Use it only when you mean "everywhere".
- `--agent <id>` makes sure the agent's ceiling includes the profile's capabilities. If they are not in the agent's explicit list, `--apply` adds them, which can raise a `bootstrap` agent to admin. Leave `--agent` out if you do not want the ceiling touched.
- Chat-scoped grants work for any contact that is not blocked or opted out. Global tags need status `allowed`.

## Recurring access for an agent

To give an agent one more capability for good, create a named profile and apply it to the agent:

```bash
ravi permissions allow cron-ops --to agent:main --capabilities execute:group:cron
ravi permissions allow cron-ops --to agent:main --capabilities execute:group:cron --apply
```

This adds the capability to the agent's ceiling under the provider-owned profile `permission-cron-ops`.

## Inspecting

| Command | Answers |
|---|---|
| `ravi permissions status` | Which providers and materializers are active |
| `ravi permissions materialize --subject-type agent --subject-id <id>` | Everything an agent holds, with the source of each capability |
| `ravi permissions materialize --subject-type contact --subject-id <id>` | A contact's global capabilities (admin tags, `--force` profiles) |
| `ravi permissions list --chat <chat-id>` | Contact grants in a chat. `--chat-tag <tag>` or `--force` for the other scopes. |
| `ravi permissions check --permission <p> --object-type <t> --object-id <id>` | Whether the current runtime context allows something |

`check` evaluates the context it runs in, so it is meant for agents inside a turn. From your own shell it reports `denied` with a note to use `materialize`. `--local-operator` checks the local operator path instead.

All `ravi permissions` subcommands accept `--json`.

## Approvals

When a turn needs a capability it does not hold, Ravi posts an approval request in the chat the turn came from.

- **Who can approve:** a contact (or agent) whose identity on that channel and instance is linked, and whose global capabilities include the requested capability or `admin:system:*`. An owner tagged `permission-owner` can approve anything. Chat-scoped grants do not make anyone an approver. Clicks or reactions from anyone else are ignored.
- **Slack:** use the **Approve** or **Reject** button. Reactions and replies are ignored.
- **WhatsApp and other channels:** react with 👍 or ❤️ to approve. Any other reaction, or a reply to the request message, rejects it.
- **Timeout:** after 5 minutes without a decision, the request is denied.
- **Scope:** an approved capability lasts for that turn only. For recurring access, use `ravi permissions allow` or `resolve`.
- **No approvals** from the terminal (`ravi sessions send`, `ravi tui`): there is no chat to ask in, so the request is denied. A `chat-only` agent's tool requests are denied without asking.

## The Bash check

Before every Bash command, Ravi checks it against the turn's capabilities. These are always blocked, under every profile, and cannot be approved:

- shells and string execution: `bash`, `sh`, `zsh`, `dash`, `ksh`, `csh`, `fish`, `tcsh`, `eval`, `exec`, `source`, `.`;
- command substitution (`$(...)`, backticks), process substitution and here-documents;
- piping into a shell, or into `python`, `python3`, `node`, `perl` or `ruby`;
- inline code: `python -c`, `python3 -c`, `node -e`, `perl -e`, `ruby -e`, `php -r`.

Below `full-access`, two more rules apply: redirecting output to a file needs `use:tool:Write`, and setting `RAVI_*` environment variables in a command is refused.

## Denials and audit

Every denial is recorded and published on the NATS topic `ravi.audit.denied`. The payload includes `agentId`, `denied`, `reason`, `blockType`, `command` (when there is one), `context`, and `denialId`.

Watch them live, or route them to an agent:

```bash
ravi events stream --only audit
ravi triggers add "Permission alert" --topic ravi.audit.denied \
  --message "A permission was denied. Explain what happened and whether I need to act." --cooldown 1m
```

Turn a denial into a fix with its `denialId`:

```bash
ravi permissions resolve <denial-id>          # plan
ravi permissions resolve <denial-id> --apply  # apply
```

`resolve` proposes a profile that holds the missing capability. For an agent denial it raises the agent's ceiling; for a denial in a governed chat it grants the profile to that contact in that chat only. `--profile` and `--capabilities` override the suggestion, and `--chat`, `--chat-tag` or `--force` override the scope.

See [Triggers](/guides/triggers) and [Events](/reference/nats-events) for more on topics.
