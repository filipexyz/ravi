By the end of this page you will have a scheduled job, know which chat its answer lands in, and know how to check each run.

A job is one of two kinds:

- **Agent job** (`--message`): sends a prompt to an agent session. The agent answers like it would in a chat.
- **Shell job** (`--shell` or `--exec`): runs a command directly. No agent, no tokens. An agent is involved only when the command fails and you asked for it with `--on-error`.

Jobs run inside the daemon, so `ravi daemon start` must be running.

## Create your first job

<Steps>
  <Step title="Add the job">
    ```bash
    ravi cron add "Morning brief" \
      --cron "0 8 * * 1-5" \
      --tz America/Sao_Paulo \
      --message "Summarize what is pending today. If nothing changed since yesterday, answer @@SILENT@@."
    ```
    The output prints the job id and the next run. `@@SILENT@@` is a token the agent can answer with to stay quiet.
  </Step>
  <Step title="Check where it runs">
    ```bash
    ravi cron show <id>
    ```
    Look at `Agent`, `Account`, `Session`, `Reply session` and the `Routing` section. They tell you which session runs the prompt and which chat gets the answer (see [Where the answer goes](#where-the-answer-goes)).
  </Step>
  <Step title="Run it once now">
    ```bash
    ravi cron run <id>            # dry-run: exit 3, shows the plan, fires nothing
    ravi cron run <id> --execute  # runs the real job now
    ```
    A manual run counts as a run: an `--every` job's next run moves one interval later, and a one-shot (`--at` or `--delete-after`) job is deleted afterwards, as after a scheduled run.
  </Step>
  <Step title="Read the result">
    ```bash
    ravi cron show <id>   # Last run, Last status, Last error
    ravi daemon logs -f   # cron:runner entries: "Executing job", "Job turn finished"
    ```
  </Step>
</Steps>

<Tip>
The easiest way to get answers in the right chat is to ask your agent, in that chat, to create the job. The agent runs `ravi cron add` from its session and the job remembers that session.
</Tip>

## Schedules

Pass exactly one of these:

| Flag | Example | Runs |
|---|---|---|
| `--cron <expr>` | `--cron "0 9 * * 1-5"` | On a five-field cron expression |
| `--every <interval>` | `--every 30m` | Every fixed interval |
| `--at <datetime>` | `--at "2026-11-03T14:45"` | Once, then the job is deleted |

**Cron expressions** use the usual five fields: minute, hour, day of month, month, day of week (0 is Sunday).

| Expression | Meaning |
|---|---|
| `0 9 * * *` | Every day at 09:00 |
| `0 9 * * 1-5` | Weekdays at 09:00 |
| `*/15 * * * *` | Every 15 minutes |
| `*/15 9-18 * * 1-5` | Every 15 minutes, 09:00 to 18:59, weekdays |
| `0 0 1 * *` | First day of the month at midnight |

`--tz` applies only to `--cron`. Without it, the job stores the `defaultTimezone` setting in effect when you add it (changing the setting later does not move existing jobs), and without that setting, it uses the timezone of the machine running the daemon:

```bash
ravi settings set defaultTimezone America/Sao_Paulo
```

**Intervals** take one positive integer and one unit: `s`, `m`, `h` or `d` (`30s`, `90m`, `2d`). Combined values such as `1h30m` are rejected. The next run is computed from the scheduled time, not from when the run finished, so intervals do not drift. The flip side: after the daemon was down, an interval job fires once for every interval it missed, back to back, until it catches up. A cron-expression job fires once and moves on.

**One-shot times** are ISO 8601. A value without an offset (`2026-11-03T14:45`) is read in the local time of the machine where you run the command. Add `Z` or an offset (`2026-11-03T14:45:00-03:00`) to be exact.

## Where the answer goes

Ravi posts an agent's answer only to a chat that is attached to the session running the turn. Which session runs the job depends on how it was created:

| Created | Default session | With `--isolated` |
|---|---|---|
| By the agent, during a chat | That chat's session. The answer goes back to that chat. | A dedicated session, `agent:<agent>:cron:<jobId>`. It has no chat of its own. |
| From your terminal | The agent's main session. The answer goes to the main session's chat, if it has one. | Same dedicated session, no chat. |

When there is no chat to post to, the answer stays in the session and the daemon logs `Response target unresolved — dropping emit`. Read the answer with:

```bash
ravi sessions read <session-name>
ravi sessions read agent:<agent>:cron:<jobId>   # an --isolated job's session
```

An `--isolated` job never posts to a chat, even when it has a reply session: a chat belongs to one session at a time, and the dedicated session is not that session. For background work in a dedicated session, tell the agent in the message how to deliver the result. For example, end the message with `Send the summary with: ravi sessions inform <your-chat-session> "<summary>"`. The session you name then answers in its own chat.

`ravi cron add` has no reply-session flag. A job the agent creates records the agent's session as its reply session; a job created from your terminal has none. To move an existing default (non-isolated) job's answers to another chat, set its reply session to the session of that chat. The job then runs in that session:

```bash
ravi cron set <id> reply-session <session-name>   # - clears it
```

`--account` (or `ravi cron set <id> account <name>`) only replaces the account on the routing source when there is one. It does not create routing on its own, and the answer still goes to the chat attached to the session. `ravi cron show <id>` shows the result under `Routing`.

### What the agent receives

The message is prefixed with the job name and the current date and time:

```text
[Cron: Morning brief 09/10/2026, 08:00]
Summarize what is pending today. If nothing changed since yesterday, answer @@SILENT@@.
```

The timestamp is always written as `dd/mm/yyyy, HH:MM` in São Paulo time, whatever `--tz` says.

## Shell jobs

Use a shell job for deterministic work (ETL, sync, scraping, scripts) that does not need an agent to think:

```bash
ravi cron add "ETL batch" \
  --cron "*/15 * * * *" \
  --shell "python3 /home/me/jobs/etl.py" \
  --timeout 5m \
  --env-file /home/me/jobs/etl.env \
  --on-error notify-session:ops
```

- `--shell` and `--exec` are the same flag. They cannot be combined with `--message`, `--isolated` or `--account`.
- The command runs through the system shell with the daemon's environment and working directory. Use absolute paths.
- `--timeout` takes seconds (`60`) or a duration (`30s`, `5m`, `1h`). The default is 10 minutes.
- `--env-file` reads `KEY=value` lines (blank lines, `#` comments and a leading `export` are allowed) and adds them to the command's environment.
- Output goes to the daemon log, not to a chat.
- On success the run records `ok`, the exit code and the duration. Nothing is sent to any agent.
- On failure (non-zero exit or timeout) the run records `error`, `lastError` with stderr, and `lastExitCode`. With `--on-error notify-session:<session>`, that session receives a `[System] Inform:` message with the command, exit code, stderr and stdout, and its agent decides what to do.
- A one-shot (`--at` or `--delete-after`) shell job is deleted only after a successful run.

## Run status

`ravi cron show <id>` and `ravi cron list --json` show `nextRunAt`, `lastRunAt`, `lastStatus` (`ok` or `error`), `lastDurationMs`, `lastError` and, for shell jobs, `lastExitCode`.

For agent jobs, the status comes from the agent turn, not from sending the prompt:

- When the prompt is sent, `lastRunAt` and `nextRunAt` move forward and the outcome fields are cleared. A run in progress shows no status.
- When the turn completes, the status becomes `ok`. When it fails or is interrupted, it becomes `error` with the runtime error in `lastError`.
- If the prompt cannot be sent at all, the job is marked `error` right away.

One-shot agent jobs (`--at` or `--delete-after`) are deleted as soon as their prompt is sent, so they never show an outcome. Use the daemon log or `ravi sessions read` to see how they went.

## Manage jobs

```bash
ravi cron list                      # from your terminal: every job; run by an agent: that agent's jobs
ravi cron list --agent <id>         # jobs of one agent
ravi cron list --all-agents         # from an agent: every agent it is allowed to see
ravi cron list --fields id,name,enabled --json
ravi cron show <id>
ravi cron disable <id>              # keep the job, stop running it
ravi cron enable <id>               # next run is recomputed from now; missed runs are skipped
ravi cron rm <id>                   # dry-run: exit 3, deletes nothing
ravi cron rm <id> --execute         # delete
```

Change a job with `ravi cron set <id> <key> <value>`:

| Key | Value |
|---|---|
| `name`, `description` | Text |
| `message` | New prompt. Turns a shell job into an agent job. |
| `shell`, `exec` | New command. Turns an agent job into a shell job. |
| `timeout`, `env-file`, `on-error` | Shell jobs only |
| `cron`, `every` | New schedule |
| `tz` | Cron schedules only |
| `agent`, `account` | Agent that runs the job, delivery account |
| `session` | `main` or `isolated` |
| `reply-session` | Session whose chat gets the answer |
| `delete-after` | `true` or `false` |

For keys that can be empty (`tz`, `agent`, `account`, `description`, `reply-session`, `timeout`, `env-file`, `on-error`), pass `-` to clear the value.

Scripts and other agents that create jobs on retries should pass `--idempotency-key <key>`. A second `add` with the same key returns the first job (status `deduplicated`) instead of creating another one. The same key cannot be reused for a different job.

## Troubleshooting

<AccordionGroup>
  <Accordion title="The job never fires">
    1. `ravi cron show <id>`: check `Enabled: yes` and `Next run`.
    2. `ravi daemon status`: the daemon must be running.
    3. `ravi daemon logs -f`: look for `cron:runner` entries.
    4. `ravi cron run <id> --execute` runs it once to separate a schedule problem from a job problem.
  </Accordion>
  <Accordion title="It runs at the wrong time">
    Check the timezone in the `Schedule` line of `ravi cron show <id>`. Without `--tz`, the job uses `defaultTimezone` (`ravi settings get defaultTimezone`) or the daemon machine's timezone. For `--at`, add an explicit offset.
  </Accordion>
  <Accordion title="It ran but nothing showed up in the chat">
    1. `ravi cron show <id>`: read `Session`, `Reply session` and `Routing`.
    2. `ravi sessions read <session-name>`: the answer may be in the session.
    3. `ravi daemon logs -f`: `Response target unresolved — dropping emit` means the session that ran the turn has no chat to post to. See [Where the answer goes](#where-the-answer-goes).
    4. If the agent answered `@@SILENT@@`, nothing is posted by design.
  </Accordion>
  <Accordion title="A one-shot job shows (expired) in ravi cron list">
    Its time has passed without a successful run (the run failed, or the time was already past when you added it), and it will not run again. Delete it with `ravi cron rm <id> --execute`.
  </Accordion>
</AccordionGroup>
