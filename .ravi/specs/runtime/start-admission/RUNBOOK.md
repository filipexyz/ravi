# Capacity refusal

Inspect `dispatch.start_rejected` / `dispatch.start_timeout` and their lane, occupants, reservations, largest consumer and queue position. `active` means resident runtimes, not necessarily executing turns; occupant `state` distinguishes them.

A person receives an `inbox_item_*` receipt in the chat. A prompt that `classifyTurnProvenance` marks `background` (cron, trigger, follow-up, observer, task, relay) posts nothing to its chat, while one it cannot classify (`unknown`) still does. After a capacity incident, look for its item with `ravi inbox list --source system --status open` (type `runtime_start_rejected`). `ravi inbox read <receipt> --json` exposes the original prompt in `item.metadata.prompt`, session identity, and capacity snapshot. The daemon resumes each saved request by itself once capacity frees up (within 4 h, and only if the session did not start another turn after the refusal). `ravi sessions retained list` shows the open ones and the plan for each; `ravi sessions retained resume <item> --execute` requeues one by hand through the normal prompt publisher as a new delivery (`--force` for a superseded or expired one; a claimed one is never requeued). The inbox events `resume_resumed`, `resume_superseded`, `resume_expired`, `resume_deferred` and `resume_failed` record each outcome. A `sessions send --wait` relay is an automation prompt too: under capacity pressure it times out without printing a receipt, and its saved item is in the same listing. Do not ask the user to repeat the message. Do not replay a source message by mutating its original receipt.

The 2026-10-31 incident logged four console-infra background starts at 11:58–11:59 with active=8, reserved=0, global max=12, background limit=8. Slots became available only at idle evictions (12:00:23 and 12:03:59); one waiter expired at 12:03:50, five minutes after admission. Another expired at 12:25:05 and an idle eviction followed ten seconds later. Existing telemetry did not enumerate occupants at timeout, so it cannot identify every slot holder retrospectively. Code reclaimed only observers during admission; ordinary idle runtimes held their slots until TTL. Prompt dispatch already used per-session tails, not a global start mutex. Presence receipt was emitted only after dispatch; native presence delivery additionally awaited every API call in a shared loop.

This fix changes source only. Applying it requires the normal reviewed deployment; no running stream, provider, route, production DB or daemon is changed by the PR.

A later thread incident had a `dispatch.start_timeout` **and a delivered timeout notice**, but no `adapter.request`. Delivery of an error is not provider execution or request recovery. The original child prompt was resumed explicitly; do not describe this as silent timeout. `sessions read` previously fell back to the parent chat when the child was empty, causing unrelated parent messages to be misdiagnosed as queued child prompts. Use canonical `session_key` trace evidence and the thread lifecycle's original prompt.

The temporary `scripts/ops/queue-recovery.py` detector checks open threads published within 24 hours, at least ten minutes old, `system_sent=false`, zero input tokens and no adapter/terminal turn. It excludes recent dispatch and reports with a four-hour cooldown. A published lifecycle counts as pending intent even if transport retention lost the trace prompt. It does not reset/replay a child: only the runtime can atomically arbitrate a concurrent start. Parent resumption uses the original thread prompt after verifying no handoff, never parent chat history.
